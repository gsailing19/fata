# fata 工程与可观测性路线图

> 最后更新：2026-08-07
> 范围：Worker 单测、CI 纳入 E2E、可观测性、算法校准。
> 原则：真实用户数据优先；不为了 14 条测试对调参；生产改动先快照。

## 1. Worker 单测与纯逻辑抽取

### 现状

- `tools/match-core.js` 已经是评分算法的单一事实源，`config/worker.js` 从它导入 `calculateScore`、`mmrRerank`、`awakeOverlapMinutes` 等纯函数。
- `findMatchInPool()`（`config/worker.js:1880`）仍是“I/O + 逻辑”混合体：拉取 GitHub Issues、解析元数据、时区过滤、语言过滤、KV 读取、解密、评分、阈值、MMR、结果组装都在一个函数里。
- 风险台账 R-11 只降级到 mitigated，因为真正未覆盖的是 `findMatchInPool` 的过滤与选择逻辑，而不是已抽出的评分函数。

### 建议抽取边界

新增 `tools/worker-match-core.js`（与 `match-core.js` 同级，可被本地测试和 Worker 共同 require）：

- `parseCandidateContext(issueBody)`：只解析公开元数据，返回 `lang`、`keyVersion`、`embeddingType`、`timezoneOffset`、`awakeReason`、`textSnippet` 等字段，不做解密。
- `evaluateCandidate(input)`：输入已经解密好的 embedding、intent、emailHash、文本片段和上下文，输出 `{ accepted, candidate, skipReason }`。内部完成语言隔离、时区硬过滤、同邮箱排除、类型不匹配、基础评分和阈值判断。
- `selectMatch(candidates, userEmb)`：候选排序 + MMR 重排 + 返回最终选择；纯函数，无网络。
- `buildMatchDebug(...)`：把 `otherSeen`、`langMismatches`、`timezoneSkips`、`timezoneSkipped`、`entries` 组装成现有 debug 结构。

`findMatchInPool` 保留为薄适配层，只负责：

1. GitHub Issues 请求；
2. KV 读取和 AES 解密；
3. 调用 `parseCandidateContext` / `evaluateCandidate` / `selectMatch`；
4. 匹配后的 email re-encrypt 和结果格式化。

不要抽取的部分：GitHub fetch、KV get/put、AES-GCM、Resend 发送、DeepSeek/SiliconFlow 调用。这些继续留在 Worker，通过集成/E2E 验证。

### 测试清单

新增 `tools/worker-match-core-test.js`，用固定 fixture，不联网、不加密：

- 时区硬过滤：重叠正好 180 分钟接受；179 分钟拒绝；一方或双方无偏移时接受。
- 语言隔离：不同语言候选直接跳过。
- 元数据解析：`_kv`、`r`、`tz`、`tzo`、`et`、`l` 的合法与非法输入。
- 同邮箱排除：hash 相同跳过。
- 上下文评分：相同原因、兼容原因、中性原因；full/good/partial/weak/unknown 时区档位；无上下文时倍率保持 1.0。
- 阈值与冷却：不同 pending 数量下的 `getEffectiveThreshold`，英文 -0.06 偏移。
- MMR：多个候选时排序确定，且与 `match-core` 的 `mmrRerank` 一致。
- 结果结构：matched/unmatched、debug 字段、`timezoneSkipped` 计数。

### 集成方式

- `tools/verify-local.js` 增加 `node tools/worker-match-core-test.js`。
- `.github/workflows/ci.yml` 的 `local-tests` job 增加同一个命令。
- 先抽取、不改行为，跑 invariant + algo zh/en + evaluate + 新测试；通过后再跑一次生产 E2E 确认线上无回归。

## 2. CI 纳入 E2E

### 约束

- `config/worker.js`、`config/wrangler.toml`、`tools/e2e-test.js`、`tools/audit.js` 当前都被 `.gitignore` 排除，公开仓库 checkout 没有这些文件。
- E2E 会真实写 GitHub Issue、调用 Resend、修改线上池；不能放进每次 push/PR 的公开 CI。
- `FATA_HMAC_KEY` 是清理 Match Issue 的必需项；缺失时 E2E 会留下测试 Issue。

### 推荐方案：私有 `fata-ops` 仓库运行受保护 CI

1. 建私有 `fata-ops` 仓库，内容包含：
   - `config/worker.js`、`config/wrangler.toml`、`config/algorithm-config.json`；
   - `tools/e2e-test.js`、`tools/audit.js`、`tools/verify-local.js` 等内部脚本；
   - `codex/private-worker/`、`codex/snapshots/`；
   - 一份独立 `.github/workflows/e2e.yml`。
2. `e2e-test.js` 改用 `FATA_WORKER_URL` 优先，不再依赖 `wrangler.toml` 解析地址，避免工作流 checkout 缺文件。
3. E2E 所有创建的 Issue 打上 `test` 标签；脚本用 `try/finally` 保证 Match Issue 清理。
4. 新增 `tools/e2e-cleanup.js`，按 `test` 标签 + 最近 2 小时 + 运行 ID 关闭残留 Issue；即使主测试失败，cleanup job 也用 `if: always()` 执行。

### 凭据策略

- 在私有仓库配置 GitHub Actions environment `production-e2e`。
- 环境 secrets：
  - `FATA_HMAC_KEY`（必须 >= 16 字符，用于清理）；
  - `FATA_WORKER_URL=https://fata.uk`；
  - 可选 `CLOUDFLARE_API_TOKEN`，只用于部署流程，不用于 E2E。
- 开启 environment protection：manual approval 后才可运行。
- 不在 workflow 中 echo secret；GitHub 自动 mask，仍禁止任何 `printenv` / debug 步骤。

### 隔离与触发

- `on: workflow_dispatch`，不接 push/PR。
- 可选夜间 `schedule`（如 `0 19 * * *` UTC），但首次只允许手动触发，跑通一周后再开定时。
- `concurrency: group: e2e-production, cancel-in-progress: false`，保证同时最多一个 E2E。
- E2E 使用唯一 `RUN_ID` 和唯一 email hash，不撞单邮箱限流；邮件固定发 `delivered@resend.dev`，不发给真实用户。

### 安全门禁

- 第一步：`node tools/verify-local.js`，失败则停止。
- 第二步：检查 `FATA_HMAC_KEY` 长度和环境是否来自 `production-e2e`。
- 第三步：`node tools/e2e-test.js`，失败不自动回滚。
- 第四步：`tools/e2e-cleanup.js` 清理；再调用 `/api/audit/stats` 或 GitHub API 断言 open test Issue = 0。
- 只有人工确认后才执行 `wrangler rollback`。

### 备选方案

如果短期不想建私有仓库，可以把 `tools/e2e-test.js` 改为公开可跟踪，并用 `FATA_WORKER_URL` 去掉 wrangler 依赖。公开 CI 仍必须走 `workflow_dispatch` + 受保护 environment，禁止 push/PR 自动执行。

## 3. 可观测性指标

### 3.1 Worker p95 延迟

定义：按 endpoint 分组，统计当天成功请求从 Worker 收到请求到返回响应的时间；只算 `/api/health`、`/api/submit`、`/api/match`、`/api/withdraw`，后续扩展到全部公开端点。

采集方式：

- 第一期：Worker 在响应前记录 `Date.now()` 差，用 beacon 同款“唯一 key + 前缀统计”写入 `RATE_LIMIT_KV`：
  `lat:<date>:<path>:<generateId>`，TTL 31 天。
- `getAuditStats` 增加按前缀读取并计算 p95；`tools/audit.js` 输出每日 p95。
- 第二期：接入 Cloudflare Analytics Engine 或 Workers Logs，避免 KV key 膨胀。

目标基线：

- `/api/health` p95 <= 1500ms。
- `/api/submit` 先记录 14 天基线，不设硬上限；之后用“连续 7 天 p95 增长 > 50%”触发告警，再定正式阈值。

### 3.2 API 成本

定义：

- SiliconFlow 成本 = BGE-M3 embedding 请求次数 + DeepSeek 共振描述 token 数。
- Resend 成本 = 匹配通知发送封数。
- Cloudflare 成本 = Workers/Pages/KV 用量，按月度账单记录。

采集方式：

- Worker 在外部 API 调用点记录唯一 key：`cost:<date>:siliconflow_embedding:<id>`、`cost:<date>:deepseek_tokens:<id>`（value 存 `{prompt_tokens, completion_tokens}`）、`cost:<date>:resend_sent:<id>`。
- 每月 1 日仍以 Resend/SiliconFlow/Cloudflare 后台为准，更新 `codex/COSTS.md`。
- `tools/audit.js` 增加“成本摘要”段，输出昨日估算次数和 token 总量。

目标基线：

- `COSTS.md` 每月有实际值，不再出现“未记录”。
- 单日估算成本超过 ¥10 告警；超过 ¥50 暂停对应端点并人工排查（沿用现有规则）。

### 3.3 邮件送达率

定义：

- `send_ok`：Worker 调用 Resend 返回 2xx。
- `delivered`：Resend Dashboard/Webhook 标记 delivered。
- `bounce`：Resend 标记 bounced/failed。
- `送达率` = delivered / (delivered + bounce)。

采集方式：

- Worker 发送成功后写 `email:<date>:sent:<id>`，审计脚本统计。
- Resend Dashboard 人工记录 delivered/bounce；若接入 Webhook，未来可自动落盘。

目标基线：

- E2E 测试发送 `send_ok` 100%。
- 累计 30 封真实通知后，送达率 >= 95%，bounce < 2%；未达之前不调邮件模板和发送策略。

### 3.4 醒着原因漏斗

定义事件链：

`page_view → select_reason → start_typing → click_send → submit_success / submit_fail → match_success / match_no_match`

采集方式：

- `handleBeacon`（`config/worker.js:490`）增加可选 `reason` 字段，写入带 reason 的唯一 key：
  `beacon:<date>:<event>:<lang>:<reason|none>:<id>`。
- `getAuditStats`（`config/worker.js:1840`）把 `select_reason` 加入事件列表，并按 reason 输出分布。
- 前端已有 `select_reason` beacon（`index.html:1423`），只需要让后端把它计入统计。

目标基线：

- 首个 50 次 page_view 周期内，各阶段数量不为 0，能看到完整漏斗。
- beacon `page_view` 与 Cloudflare PV 偏差 < 20%（沿用现有目标）。
- 转化率前 30 个真实会话只记录、不设死阈值。

### 3.5 提交成功率与匹配率

定义：

- 提交成功率 = `submit_success / (submit_success + submit_fail)`。
- 匹配率 = `match_success / (match_success + match_no_match)`，只在提交成功后统计。

采集方式：

- 直接复用 beacon 已存在的 7 个事件，加上 `select_reason` 后共 8 个。
- `getAuditStats` 返回今日/昨日分语言聚合；`tools/audit.js` 写入日志并显示趋势。

目标基线：

- 累计 50 次真实提交后，提交成功率 >= 95%。
- 匹配率先记录基线，不设目标；真实池 >= 100 个 pending 后再校准。

## 4. 算法校准

### 4.1 英文 F1

现状：

- `tools/algo-test.js --lang en` 当前 84.2%，只有 3 个已知 FP。
- 样本规模小，继续在现有测试对上调权重很容易过拟合。

策略：

1. 冻结当前参数作为基线，不动 `ALGORITHM_CONFIG`。
2. 从真实英文提交中积累配对样本，至少 30 对后建立训练/验证集。
3. 使用 `tools/tune-params.js` 只在训练集上搜索；验证集必须有未参与调参的新样本。
4. 候选参数必须满足：英文验证 F1 提升 >= 3 个百分点、invariant 全绿、中文 F1 不下降、现有 en 测试无新增回归。
5. 任一条件不满足就保持当前基线。

验收标准：真实样本不足时不调参；有 30 对真实样本后才允许改权重或阈值。

### 4.2 3 小时时区窗口

现状：

- R-14 只在双方都有 `timezoneOffset` 时执行硬过滤；旧 seed 无偏移，不受影响。
- 当前 180 分钟阈值尚未有真实池数据验证。

策略：

1. 通过 `/api/find` debug 或审计脚本持续记录 `timezoneSkipped`、`otherSeen` 和 `match_success / match_no_match`。
2. 计算时区跳过率 = `timezoneSkipped / otherSeen`。
3. 在真实池数据不足时不改 180 分钟。
4. 如果连续两周匹配率 < 5% 且跳过率 > 30%，先用 `simulate-pool.js` 对历史 Issue 元数据离线模拟 120/150/180 分钟，选择离线效果更好的值。
5. 任何改动先快照，再部署，再 E2E。

验收标准：真实带时区偏移的 pending >= 50 条之前，阈值保持 180 分钟；离线模拟 + 真实回测均改善后才调整。

## 5. 优先级与验收标准

| 优先级 | 项目 | 验收标准 |
|--------|------|----------|
| P0 | Worker 纯逻辑抽取 + 单测 | `tools/worker-match-core-test.js` 覆盖过滤/评分/选择/MMR/结果结构；`verify-local` 与 CI 全绿；抽取不改行为，生产 E2E 15/15 |
| P0 | 可观测性基线 | `select_reason` 进入审计统计；延迟 key、成本 key、邮件 key 落地；`METRICS.md` / `COSTS.md` 不再写“未记录” |
| P0 | 文档与数字同步 | `VERIFY.md` 改为 invariant 70、E2E 15/15；`TASKS.md`、`METRICS.md` 日期和基线同步；作为后续任务的前置项 |
| P1 | CI 纳入 E2E | 私有 `fata-ops` 或受保护 workflow 可手动运行；失败有清理步骤；open test Issue = 0；secrets 不出现在日志 |
| P1 | 移除 `_kv<=3` 兼容路径 | 历史脱敏复查 sensitive=0；Worker 不再读取旧格式；E2E 通过后删除兼容分支 |
| P1 | 邮件送达率闭环 | 累计 30 封真实通知后，Resend 送达率 >= 95%，bounce < 2% |
| P2 | 英文 F1 校准 | 30 对真实英文样本 + 验证集；F1 提升 >= 3 个百分点且无回归 |
| P2 | 时区窗口校准 | 50 条带偏移真实 pending；离线模拟 + 真人回测均改善后才调整 |
| P2 | Model2Vec / PWA / 高级信纸 | 等真实用户反馈和回测数据，不进入无人值守自动改动 |

### 执行顺序建议

1. P0 文档同步，避免后续依据过期数字做决策。
2. P0 Worker 纯逻辑抽取 + 单测，这是 CI E2E 和移除旧兼容路径的地基。
3. P0 可观测性基线，在冷启动真实用户到来前先有数据通道。
4. P1 CI E2E，作为每次生产 Worker 改动后的受控验收。
5. P1 移除 `_kv<=3` 兼容路径，必须排在 P0 单测和 E2E 之后。
6. P2 算法校准，等真实数据，不闭门调参。
